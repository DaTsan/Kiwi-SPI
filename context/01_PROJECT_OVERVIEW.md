# 01. Обзор проекта Kiwi-SPI (Kiwi TCMS)

## 📌 Что это за проект?

**Kiwi-SPI** — репозиторий на базе **Kiwi TCMS**, ведущей открытой системы управления тестированием (Test Case Management System, TCMS) для ручного и автоматизированного тестирования.

Kiwi TCMS предоставляет полноценную среду для организации процессов обеспечения качества (QA), планирования тестовых циклов, ведения базы тест-кейсов, трекинга запусков (Test Runs) и результатов выполнения (Test Executions), а также тесной интеграции с внешними баг-трекерами и инструментами автоматизации.

---

## 🎯 Основные цели и возможности

1. **Управление тест-планами и тест-кейсами**:
   - Древовидная организация тест-планов (`django-tree-queries`).
   - Поддержка параметров тестов, версионирования содержимого через `django-simple-history`.
   - Шаблоны тестов, шаги выполнения, предусловия и постусловия.
   - Поддержка Markdown и форматирования с подсветкой синтаксиса.

2. **Организация и выполнение тестовых прогонов (Test Runs)**:
   - Создание прогонов под конкретные сборки (`Build`), версии (`Version`) и продукты (`Product`).
   - Назначение ответственных тестировщиков (`default_tester`, `assignee`).
   - Генерация матриц тестирования (полная комбинаторика и Pairwise-тестирование с использованием `allpairspy`).
   - Учет времени выполнения (setup duration, testing duration).

3. **Интеграция с системами отслеживания ошибок (Issue Trackers)**:
   - Встроенный баг-трекер (`tcms.bugs`).
   - Интеграция в 1 клик с популярными внешними баг-трекерами: **Jira**, **GitLab (CE/EE/SaaS)**, **GitHub**, **Bugzilla**, **Redmine**, **Azure Boards**, а также межсерверная интеграция с другими инстансами **Kiwi TCMS**.

4. **Автоматизация и расширяемый API**:
   - Полноценный API на протоколах **JSON-RPC 2.0** и **XML-RPC** (`tcms.rpc`), позволяющий взаимодействовать любым автотестам и CI/CD пайплайнам (Jenkins, GitLab CI, GitHub Actions).
   - Клиентская библиотека `tcms-api` и плагины для популярных тест-раннеров (pytest, Robot Framework, JUnit, TestNG и др.).

5. **Телеметрия и отчетность (`tcms.telemetry`)**:
   - Дашборды статусов выполнения тестов (Execution Dashboard).
   - Аналитика покрытия, трендов (Execution Trends), матрица статусов (Status Matrix).
   - Оценка стабильности и состояния тест-кейсов (TestCase Health).

6. **Многопользовательская безопасность и права доступа**:
   - Гранулярные права на уровне объектов (`django-guardian`).
   - Поддержка ролей, групп пользователей, подтверждения регистраций и капчи (`django-simple-captcha`).
   - Поддержка многоарендности (Multi-tenancy / `django-tenants`).

## 🏛 Доменная модель сущностей

Иерархия предметной области строится вокруг следующих базовых цепочек:

```
[Classification]
       │
       ▼
   [Product] ───► [Component]
       │
       ├───► [Version] ───► [Build]
       │
       ├───► [Category]
       │
       ▼
  [TestPlan] ─── (Tree: Parent/Children)
       │
       ├───── 1:N ─────► [TestCasePlan] ◄───── M:N ─────► [TestCase]
       │                                                     │
       ▼                                                     ▼
   [TestRun] ───────────────────────────► [TestExecution]
       │                                         │
  (Build, Env)                                   ├─────► [Bug] (Внутренний)
                                                 └─────► [LinkReference] (Внешний баг-трекер)
```

### Основные сущности:
- **`Classification`**: Верхнеуровневая группировка продуктов (например, "Enterprise", "Embedded", "Internal Tools").
- **`Product`**: Конкретный программный продукт или сервис.
- **`Version`**: Версия продукта (например, `1.0.0`, `2.0-rc1`).
- **`Build`**: Конкретная сборка/билд в рамках версии (например, `build-1042`).
- **`Component`**: Компонент системы (например, `Auth Service`, `Billing`, `UI`).
- **`TestPlan`**: План тестирования, содержащий цели, ссылки, метаданные и набор тест-кейсов. Поддерживает древовидную иерархию (родительские и дочерние планы).
- **`TestCase`**: Единичный тест-кейс со статусом (`CONFIRMED`, `PROPOSED` и т.д.), приоритетом, шагами, скриптами автоматизации и историей изменений.
- **`TestCasePlan`**: Промежуточная связь многие-ко-многим с кастомным порядком (`sortkey`) кейса внутри плана.
- **`TestRun`**: Конкретный запуск плана тестирования для определенного билда.
- **`TestExecution`**: Конкретное исполнение тест-кейса в рамках тест-рана (статусы: `IDLE`, `PASSED`, `FAILED`, `BLOCKED`, `ERROR`, `WAIVED` и др., время старта/окончания, тестировщик).
- **`Bug` / `BugSystem`**: Связь обнаруженного бага с запуском теста и внешним трекером.

## 💻 Стек технологий

| Категория | Технологии / Библиотеки |
| :--- | :--- |
| **Язык разработки** | Python 3.12+ |
| **Бэкенд-фреймворк** | Django 6.1.1 |
| **Базы данных** | PostgreSQL (`psycopg 3.3.5`), MariaDB / MySQL (`mysqlclient`), SQLite (для локальных тестов) |
| **RPC & API** | `django-modern-rpc 2.1.0` (JSON-RPC 2.0, XML-RPC) |
| **Контроль доступа** | `django-guardian 3.4.1` (Object-level permissions), встроенная Django Auth |
| **История изменений** | `django-simple-history 3.13.0` |
| **Иерархические структуры** | `django-tree-queries 0.25.1` |
| **Внешние интеграции** | `jira`, `PyGithub`, `python-gitlab`, `python-redmine`, `python-bugzilla`, Azure Boards REST API |
| **Фронтенд** | PatternFly, Webpack 5.110.3, Babel, jQuery, Grappelli Admin Theme |
| **Инфраструктура** | Docker, Nginx, uWSGI, Helm Charts (Kubernetes) |
| **Тестирование и QA** | `pylint` + `kiwi_lint`, `flake8`, `bandit`, `coverage`, `locust` (нагрузочное тестирование), Robot Framework, Selenium |
