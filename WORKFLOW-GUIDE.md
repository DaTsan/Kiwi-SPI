# Планирование и пошаговое выполнение

Новый раздел: http://127.0.0.1:8000/workflow/ — меню **WORKFLOW**.
Интерфейс новых страниц пока на английском; ниже приведен рабочий маршрут.

## Первый цикл тестирования

1. В стандартном Kiwi создайте Product, Version/Build и TestPlan. Добавьте
   кейсы в план и переведите готовые кейсы в подтвержденный статус.
2. Откройте кейс → **Structured steps & custom fields**. Нажмите
   **Add step / shared set**, заполните Action и Expected, сохраните.
   Стрелки меняют порядок, Remove удаляет шаг после сохранения.
3. В WORKFLOW → **Planning** выберите продукт, создайте **New milestone**
   со сроками, затем **New cycle** с этой milestone.
4. Откройте цикл → **Create configuration runs**. Выберите план и активную
   сборку именно его версии. Можно выбрать несколько Environment, созданных
   через ADMIN: для каждого появится отдельный запуск. Без Environment
   создается один запуск. В него входят подтвержденные кейсы выбранного плана.
5. Откройте запуск → исполнение кейса. Укажите статусы шагов и Actual,
   общий Status, Comment, Elapsed time в секундах и Defect references.
   **Save result** добавляет попытку. Успешный общий результат требует
   успешных статусов всех шагов.
6. Повторное сохранение создает следующую попытку. В **Result history**
   остаются предыдущие результаты, авторы, время и детали шагов.
7. **My tasks** показывает назначенные вам незавершенные и отрицательные
   исполнения открытых запусков. **Progress & reports** показывает прогресс
   и позволяет скачать CSV. В цикле и milestone есть ссылка **Report / CSV**
   с соответствующим фильтром.

Существующий запуск можно привязать в цикле через **Add an existing run**
или на новой странице запуска через форму планирования. Один запуск входит
в один цикл и одну milestone; milestone запуска должна совпадать с milestone
цикла. Закрытый запуск нужно открыть в стандартном редакторе, прежде чем
добавлять результаты.

## Общие шаги и поля

**Planning → Shared step library → New shared step set** создает общий
процедурный блок продукта. В редакторе кейса выберите Shared в отдельной
строке, оставив Action/Expected пустыми. Изменения библиотеки отражаются в
кейсе; снимки уже созданных исполнений сохраняются.

Администратор может создать **New custom field** для Test case или Test result:
Text, Integer, Checkbox, Select, Date, URL. Key — постоянный технический ключ;
для Select варианты задаются по одному на строку. Required делает поле
обязательным. Флажок со значением False и число 0 являются допустимыми.
Неиспользуемое поле можно деактивировать. Тип и ключ созданного поля
не меняются, чтобы не исказить сохраненные значения.

## Совместимость и ограничения первой версии

- Обычные страницы Kiwi, Markdown, комментарии, вложения, API и матрицы
  остаются доступны. Из стандартного запуска есть кнопка
  **Step execution, results & planning**.
- Результаты нового режима обновляют обычный статус исполнения Kiwi.
  Изменения через прежний интерфейс/API остаются в прежней истории;
  отдельную пошаговую попытку они не создают.
- Новое исполнение получает снимок кейса, шагов и полей при создании.
  Старое исполнение получает снимок текущего определения при первом
  открытии нового режима; на странице это явно отмечено.
- При клонировании кейса в другой продукт общие блоки становятся обычными
  шагами. Переносятся только совместимые поля с одинаковыми ключами и типами;
  обязательные поля целевого продукта нужно заполнить в новом черновике.
- Связь milestone с родителем задает иерархию. Прогресс milestone учитывает
  непосредственно привязанные запуски; подчиненные milestone показываются отдельно.
- На экране отображается до 100 объектов раздела и до 1000 исполнений/строк
  отчета. CSV содержит весь результат выбранного фильтра. Полноценная пагинация
  и расширенные сохраненные представления входят в последующие этапы.
- Импорт TestRail, datasets, rerun подмножества, согласования и API новых
  сущностей пока не реализованы. Полный план — TESTRAIL-GAP-ANALYSIS.md.

## Запуск тестов

Из папки этого проекта при работающем Docker Desktop:

```powershell
docker compose -f compose.test.yaml build tests
docker compose -f compose.test.yaml run --rm tests
```

Тесты используют временную SQLite внутри одноразового контейнера. К базе
MariaDB локального приложения они не подключаются. При изменении зависимостей
или статических ресурсов пересоберите тестовый образ перед проверкой.
