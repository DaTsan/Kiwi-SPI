# TestRail → Kiwi-SPI: анализ и план функционального сближения

Дата анализа: 11 октября 2026 года. База: Kiwi-SPI 16.4, `624f819c8`.
Исследование опирается на публичную документацию TestRail, а сравнение Kiwi —
на исходный код этого репозитория. Платная учетная запись TestRail и проверка
его закрытого интерфейса не использовались. Названия тарифов и доступность
отдельных Enterprise-возможностей нужно проверять перед коммерческим выбором.

## Что представляет собой TestRail

Это хранилище тестов и система управления тестированием: проекты содержат
наборы/разделы и кейсы; из кейсов формируются тесты в запусках; планы группируют
запуски, в том числе для разных конфигураций; milestones связывают тестирование
с релизами и сроками. Результат выполнения — самостоятельная запись с автором,
статусом, комментарием, затраченным временем и дефектами. Для структурированных
сценариев фиксируются результаты отдельных шагов.

Сильные стороны рабочего процесса: повторное использование шагов, настройка
полей без программирования, назначение задач, история результатов, сводки
прогресса на уровне запуска/плана/milestone/проекта и интеграция через API.
Документация также описывает восстановление версий, параметризацию и наборы
данных, согласования, аудит и интеграции автоматизации.

## Соответствие понятий

| TestRail | Kiwi-SPI сейчас | Решение |
| --- | --- | --- |
| Project | Product | Использовать Product как область данных |
| Suite / section | TestPlan с деревом + Category | Сохранить существующую структуру |
| Test plan — группа запусков | TestPlan — преимущественно набор кейсов | Добавить отдельный цикл тестирования, не менять смысл существующих планов |
| Run / test | TestRun / TestExecution | Расширять существующие сущности |
| Configurations | Environment + Property + full/pairwise matrix | Использовать существующие окружения для создания отдельных запусков |
| Milestone | Прямого аналога нет | Добавить релизные вехи со сроками и прогрессом |

## Объем первой реализации

Реализовать F01–F07 отдельным Django-приложением `tcms.workflow` и встроить его
в меню, карточки кейсов и запусков. Не заменять существующий JSON-RPC, историю,
Markdown и матрицы. Существующие статусы определять по `weight`, а не по имени:
`> 0` — успешный, `< 0` — отрицательный, `0` — незавершенный. Это сохраняет
совместимость с пользовательскими статусами Kiwi.

Результаты нового пошагового режима добавляются отдельными записями и обновляют
обычный TestExecution, поэтому существующая telemetry продолжает видеть статус.
Старые комментарии и история остаются доступными в стандартном интерфейсе.
Новые запуски получают снимок шагов при создании исполнения; изменения кейса
или общего блока не переписывают уже начатое тестирование. Для старых исполнений
снимок создается при первом открытии нового режима; прежние шаги задним числом
восстановить невозможно, поскольку их раньше не было в структурированном виде.

Цикл создания запусков выбирает готовые Environment. Каждое выбранное окружение
создает отдельный запуск. Полная комбинация независимых групп конфигураций в
стиле TestRail остается дальнейшим расширением; существующая матрица Kiwi
продолжает работать внутри запуска.

## Критерии приемки и тесты

1. Пользователь создает milestone, добавляет цикл и запускает кейсы для двух
   окружений; прогресс показывает фактические результаты связанных исполнений.
2. Кейс использует собственные и общие шаги; изменение библиотеки обновляет
   определение кейса, но сохраняет снимки ранее созданных исполнений.
3. В результате сохраняются статусы шагов, actual, комментарий, время, дефекты,
   custom fields и автор. Повторная попытка добавляет историю, не затирает ее.
4. Пустое обязательное поле, неправильный тип, поле чужого продукта, неверные
   даты, циклическая milestone и несовместимый Build отклоняются без частичной записи.
5. Права проверяются на чтение и изменение. Анонимные/ограниченные пользователи
   не получают данные через прямой URL, формы, отчеты или экспорт.
6. POST защищены CSRF; пользовательские значения экранируются; CSV защищен
   от формул из названий и комментариев.
7. Новые тесты и затронутые существующие Django-тесты запускаются в отдельном
   контейнере на временной SQLite. Тесты не подключаются к локальной рабочей MariaDB.
8. После применения миграций выполняется HTTP-проверка локального стенда.

## Границы работы

Файлы меняются только внутри `C:\Users\prode\Desktop\kiwi`.
Используются только контейнеры Compose-проектов `kiwi-spi-local` и
`kiwi-spi-tests`. Другие папки, контейнеры, базы и настройки компьютера не
меняются. Полная функциональная идентичность TestRail не заявляется: F08–F16
остаются явно отмеченным планом следующих этапов.
